# 第 4 階段驗收報告：附件三階段處理與一致性

- 狀態：**自測通過，待複驗**。真實 ClamAV 已於第 8 階段補驗。
- 日期：2026-10-30。分支 `p0-baseline-hardening`，未 commit。測試資料：`tmp/ai-attachments/`（合成檔，全部標示測試）。

流程：**選檔 → 本機預覽與處理狀態 → 上傳原檔、真實格式與安全檢查（無 AI）→ 按「確認並檢查」才送 AI → 通過自動加入，有提醒則請使用者確認 → 草稿附件區顯示同一檔案預覽。**

## 1. 修改摘要

| 根因（實測重現） | 修正 | 檔案 |
|---|---|---|
| **上傳後立刻跑 AI 統編檢查**，選檔就把檔案送給模型 | 上傳路徑只做真實格式與安全掃描；AI 檢查由「確認並檢查」啟動 | `staged-upload/route.ts`、`actions.ts`、`staged-invoice.ts` |
| **`sniffAllowedType` 回傳字串，程式卻讀 `.mime`**（既有的型別錯誤其實是真 bug）→ 聊天上傳的 **HEIC 與 PDF 全部被拒絕** | 修正判斷 | `staged-images.ts` |
| **所有上傳入口都先在瀏覽器有損重壓縮**（長邊 1600、品質 0.78），原始證據遺失 | 移除壓縮，聊天、表單、附件面板都上傳原檔；分析用的較小副本只用於模型，不取代原檔 | 刪除 `client-image-optimize.ts`；`attachments-panel.tsx`、`pending-files-field.tsx`、`ai-chat-app.tsx` |
| AI 檢查綁在請求上，大檔或模型慢時整個請求卡住 | 背景執行並輪詢；有逾時（`ATTACHMENT_ANALYSIS_TIMEOUT_MS`）、失敗可重試；工作中斷（重啟）會在讀取時標為「未完成檢查」 | `staged-invoice.ts` |
| PDF 以 `image/jpeg` 送模型；頁數永遠是 1 | 以真實類型送；記錄實際頁數。超過可內嵌大小的 PDF 取前 5 頁檢查，並在摘要標明「只檢查前 N 頁」 | `invoice-vision.ts`、`invoice-check.ts`、`staged-invoice.ts` |
| 模型把 8 位統編數錯後自行清空；看不清的極小字仍猜數字並判定「不符」 | 模型只抄寫，格式由後端判斷；信心低時一律 `unclear`，不下符合／不符結論 | `invoice-vision.ts`、`tax-id.ts`（含單元測試） |
| 夾入目標在點擊當下才決定，切換草稿會誤掛 | 目標在「確認並檢查」時固定；之後切換草稿，提醒卡會指出差異並讓使用者改選；確認紀錄綁定草稿 | `image-attachments.tsx`、`attach-staged.ts` |
| 版本衝突時檔案已先寫入；重複夾入也遞增版本 | 以交易包住版本檢查與關聯，全部成功或全部不變；已在草稿上的檔案不重複、不遞增版本 | `attach-staged.ts` |
| 關聯成功才可顯示成功 | 只有伺服器回報已關聯的檔案才離開清單並顯示「已加入」；失敗顯示「尚未加入」與「重新加入草稿」 | `image-attachments.tsx`、`ai-chat-app.tsx` |
| 分析結果沒有記錄用哪個檔案、哪版公司設定 | 新增 `analysis_content_sha256`、`analysis_company_version`、`analysis_rules_version`；提醒確認紀錄也寫入公司設定版本 | `0035_staged_analysis_provenance.sql`、`staged-invoice.ts` |
| 同一對話累計 10 個附件後就不能再上傳 | 改為短時間上傳量的資源保護（不是對話終身上限） | `staged-images.ts` |
| HEIC 無法預覽 | 伺服器以 `?preview=1` 轉 JPEG 預覽，原檔不變；聊天與草稿區都適用 | `staged/[id]/route.ts`、`draft-files/.../route.ts`、`draft-attached-files.tsx` |
| 檔案數量、大小散落各處 | 集中到 `policy.ts`（`MAX_CHAT_ATTACHMENTS`、`ANALYSIS_TIMEOUT_MS`、`ANALYSIS_MAX_INLINE_BYTES`），可用環境變數調整 | `policy.ts` |
| 暫存檔沒有清理機制 | 新增 `scripts/purge-staged-attachments.ts`（預設 7 天，需排程） | `staged-images.ts` |

## 2. 測試結果

### 2.1 腳本（真實 Gemini＋固定測試組，判定讀 DB 與儲存檔案）

`npx tsx scripts/ai-accept-s4.ts --out report.json`（需 `DATABASE_URL`、`STORAGE_LOCAL_PATH`）→ **20 通過、0 失敗、1 未驗證**（`evidence/S4/backend-cases.json`）

| 情境 | 結果 |
|---|---|
| 選檔未確認 | DB `analysis_status`、`analysis_started_at` 皆為空 |
| 無損最佳化沒有收益／原檔保留 | 不再壓縮；儲存檔雜湊與來源檔相同，草稿附件雜湊亦同 |
| 大檔案 | 6 MB PNG 原檔保留；33.8 MB、30 頁 PDF 未被拒絕，取前 5 頁檢查並在摘要標明 |
| HEIC、多頁 PDF | 真實 `image/heic` 判定為 match；3 頁 PDF 記錄 3 頁 |
| 統編符合 | `match`，加入指定草稿 |
| 統編不符／缺少／模糊 | `mismatch`／`not_found`／`unclear`，分開呈現；確認只對指定草稿有效 |
| AI 無法辨識或逾時 | `analysis_failed`，`complete=false`，需確認才可夾帶，不算通過 |
| 非發票照片 | `not_invoice`，買方統編與金額為空，未捏造 |
| 損毀、偽裝 MIME | 損毀 JPEG → `analysis_failed`；`.jpg` 檔名的 PDF 判定為 `application/pdf` |
| 重試、連點 | 並行重送 2 次，附件 1 個，版本不變 |
| 附件關聯失敗（故障注入） | 回報失敗、附件 0 個；重試後 1 個 |
| 公司資訊權限 | 一般員工修改被拒 |
| 分析版本 | 記錄檔案雜湊、公司設定 v1、規則 `invoice-rules-2` |
| 安全掃描失敗 | **替身 clamd**：含 EICAR 的 PDF → `infected`，不可夾帶；內容不是 PDF 的檔案在掃描前就被拒 |
| 真實 ClamAV | **通過**：`clamav/clamav-debian:1.4.6`，PDF 串流內含 EICAR → `infected` 並隔離、不可夾帶；乾淨 PDF 通過（`evidence/S8/real-clamav-s4.json`） |
