# 企業內部電子採購與簽核系統 — 第一期設計文件

- 日期：2026-07-10
- 狀態：已核准（待轉入實作計畫）
- 範圍：第一期 —「四張表單線上化 + 簽核流程」

## 背景

台灣智慧駕駛股份有限公司（Turing Drive Inc.）目前的採購與費用申請流程完全依賴紙本簽核與 Excel 範本
（`reference/20260709_請採驗費用申請單.xlsx`），搭配部分流程使用「104 企業大師」線上表單。核心規範見
`reference/20260605_採購管理辦法.pdf` 與 `reference/20260623_費用申請流程說明.pptx`。

現況痛點：
- 四張表單（請購單、採購單、驗收單、費用申請單）與簽核鏈全靠人工傳遞紙本或 Excel 檔案，效率低、易漏簽、難追蹤進度。
- 單號需人工向財會索取，容易出錯或重複。
- 主檔資料（員工、部門、預算、供應商）分散在 Excel 的 `link` 工作表，缺乏統一維護介面。

本文件為第一期範圍的設計規格，目標是把「請購單 → 採購單 → 驗收單 → 費用申請單」的四表單流程與其簽核鏈
完整搬上線，取代紙本傳遞與人工判斷簽核順序的部分。

### 文件版本間發現的差異（已與需求方確認的現況修正）

在整理現有文件時發現三處新舊版本不一致，已確認以**最新版本**為準：

1. 請購單號核發單位：舊版「總務」→ 現為「財會/會計」
2. 廠商付款日：xlsx「各項支出報支規定」仍寫「次月30號」→ 實際已改為「次月25號」（以 PPTX 2026/3/16 版與 xlsx 表單本身為準）
3. 材料列入庫存管理門檻：舊版 NT$5,000 → 新版 NT$10,000

## 架構與技術棧

- **框架**：Next.js（App Router），前後端合一，使用 Server Actions 處理表單提交與簽核動作
- **資料庫**：Supabase Postgres，搭配 Row Level Security（RLS）依角色/部門限制資料存取
- **登入**：Supabase Auth 串接 Google OAuth，僅限公司網域帳號登入
- **檔案儲存**：Supabase Storage，存放報價單、發票/收據、送貨單、銀行存摺封面等附件
- **通知**：系統內通知（存於 DB，登入後顯示待辦清單）+ Email 雙重提醒
- **部署**：Next.js 部署於 Vercel，Supabase 作為 BaaS 後端（Auth／DB／Storage／RLS 集中在同一服務）

### 部署與帳號治理注意事項

系統會存放員工與供應商的銀行帳戶等財務隱私資料。開發階段使用開發者個人 Supabase／Vercel 帳號進行快速
迭代，**但正式上線收真實資料前，必須完成以下轉移**：

1. 在 Supabase 建立公司名義的 Organization（公司 email 網域），將專案 transfer 進去
2. Vercel 專案改用公司 Team 帳號
3. 兩邊帳單改為公司發票、並限制成員存取權限

此項為上線前的強制檢查項，需在實作計畫的最後階段列為明確任務。

## 資料模型

### 主檔資料（第一期：管理員手動維護 + 從現有 xlsx 匯入種子資料，不做外部系統同步）

- `departments`：部門代碼、部門名稱、部門主管
- `employees`：工號、姓名、部門、職稱、Google 帳號 email、角色（一般員工/部門主管/預算負責人/財會/管理員）
- `budget_codes`：預算編號、部門/專案、中項分類（人事費/租金/材料/設備等）、預算負責人、年度預算金額
- `suppliers`：客戶/供應商資料卡欄位（公司名稱、統編/註冊編號、地址、聯絡人、往來銀行資訊、幣別）

### 表單與流程資料

- `procurement_cases`：一個採購案的容器，對應「請購單號」（編碼規則：CP + 民國年月5碼 + 流水號4碼），串接底下四張表單
- `purchase_requests`（請購單）、`purchase_orders`（採購單）、`acceptances`（驗收單）、`expense_requests`（費用申請單）：各自的表頭 + 明細項次（項目、預算編號、數量、金額等）
- `approval_steps`：每張表單一組簽核鏈記錄（簽核順序、簽核人、狀態：待簽核/核准/退回、簽核時間、意見）
- `attachments`：關聯到表單，存 Supabase Storage 的路徑與檔名
- `notifications`：待辦通知記錄（已讀/未讀）

單號由系統原子遞增產生，取代現行「向財會取號」的人工流程；四張表單共用同一案件單號
（如 CP112090001，項次分別為 A1 請購 / B1 採購 / C1 驗收 / D1 費用申請）。

## 簽核流程引擎

### 簽核鏈產生規則

系統依表單金額與部門自動算出簽核鏈，不需人工指定：

1. 申請人（表單建立者）
2. 申請單位主管（依 `employees.部門` 對應 `departments.部門主管`）
3. 預算負責人（依表單所選 `budget_codes.預算負責人`，可能與部門主管不同人）
4. 總經理核決；**該表單本身金額**（非整案累計金額）> NT$100,000 時，需再加簽董事長

### 流程串接規則

- 四張表單依序進行：請購單核准通過後才能建立採購單，採購單核准通過後才能建立驗收單，以此類推
- 每張表單各自跑一輪完整簽核鏈（最多 4 個層級），非整案僅簽一次
- 例外：付款條件為「預付款」時，可跳過驗收單直接進費用申請單，待貨到後再補驗收

### 簽核動作

- **核准**：進入下一位簽核人；若已是最後一關，表單狀態轉為「已核准」，解鎖下一張表單的建立
- **退回**：需填寫退回原因，表單狀態轉為「待修改」，回到申請人手上；申請人修改後重新送出，簽核鏈從第一關重新跑

## 表單欄位與附件

沿用現行 xlsx 表單結構作為線上表單欄位設計依據：

| 表單 | 表頭欄位 | 明細欄位 | 附件 |
|---|---|---|---|
| 請購單 | 案件單號、申請單位、申請人、請購日期、預計需求天數 | 預算來源、項目（材料/設備等）、預算編號、說明、數量、預估費用 | （通常無） |
| 採購單 | 預計採購廠商、付款方式、付款條件、預計交貨天數 | 同請購單項次+單價+總價 | 報價單、合約、供應商資料卡 |
| 驗收單 | 承攬廠商、驗收日期 | 各項次 Pass/Fail、財產編號（財會填） | 送貨單、驗收文件（對帳單/照片等） |
| 費用申請單 | 付款對象、付款方式、期望付款日、銀行資訊 | 各項次金額 | 發票/收據掃描檔 |

### 欄位驗證規則（沿用現行注意事項，系統自動檢查）

- 「設備」vs「材料」判斷：未稅金額 ≥ NT$80,000 且非隨車出售 → 設備，否則材料
- 報價單家數對應採購金額門檻：<NT$30,000 需1家、NT$30,000~99,999 需2家、≥NT$100,000 需3家；未達門檻家數需填寫「未檢附其他報價單原因」
- 廠商報價單付款條件需與費用申請單期望付款日一致，不一致時系統提示但不強制擋單
- 發票/收據買受人抬頭正確性（台灣智慧駕駛股份有限公司/統編 50773141，或國外 TURING DRIVE INC.）屬單據影像內容，系統無法自動判讀，僅列檢查清單提醒申請人自行核對

### 附件上傳

每張表單可上傳多個檔案（PDF/圖片），存 Supabase Storage，簽核畫面可直接預覽，不需下載。

## 通知與付款週期整合

### 通知

- 表單進入簽核佇列時：建立 `notifications` 記錄 + 寄送 Email（含表單摘要與直接連結）
- 表單被退回時：通知原申請人
- 表單完成核准／案件全部完成時：通知申請人與財會

### 財會撥款週期提示

沿用現行固定付款日規則，系統自動計算「預計付款批次」，不強制卡關：

- 員工代墊：每月 15 號、30 號兩批，收件截止為付款前 5 個工作天
- 外部廠商：每月 25 號一批，收件截止為付款前 5 個工作天；急件（付款前 2 個工作天內送件）需先經部門主管 Email 同意才能送件
- 若「期望付款日」未填，系統自動以「發票月份次月 25 號」計算
- 費用申請單核准後，系統顯示「預計撥款批次日」給申請人與財會參考；實際入帳仍由財會人工執行，第一期不做自動轉帳/自動產生傳票

## 錯誤處理與例外情境

- 表單金額為 0 或明細為空：禁止送出
- 附件缺件：允許送出但標記「憑證待補」，核准後可在案件頁面補傳；財會撥款前需確認補齊，逾期系統顯示提醒但不自動撤銷申請
- 驗收 Fail：該項次標記退貨/異常，仍可送出驗收單，但費用申請單對應項次需人工排除或另行處理（第一期不做自動退款/折讓單模組）
- 簽核人離職/請假：第一期支援管理員手動指派代理簽核人，不做自動轉派邏輯
- 併發送出同單號：案件單號由系統原子遞增產生，避免重複

## 測試策略

- **單元測試**：簽核鏈產生邏輯（依部門/預算負責人/金額門檻算出正確簽核順序）、單號產生邏輯、付款批次日計算、設備/材料判斷邏輯
- **整合測試**：四表單依序解鎖流程、退回重簽流程、預付款跳過驗收的例外路徑
- **人工驗收測試**：使用 xlsx 範例資料跑過 2-3 個真實案例的完整申請人→主管→預算負責人→總經理四表單流程，確認畫面與現行紙本表單欄位一致
